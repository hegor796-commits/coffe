# Coffee Pre-Order — платформа предзаказа кофе

White-label сервис предзаказа кофе. Одно **Telegram Mini App** с тремя ролями:
**клиент** заказывает, **бариста** видит ленту заказов и ведёт их по статусам,
**админ** (владелец) настраивает меню, точки и сотрудников. Мультитенантный —
одна инсталляция обслуживает много кофеен.

Оплата на MVP — **при получении на кассе** (без интеграции с POS). Онлайн-оплата
(ЮKassa с ключами кофейни) заложена в модель как режим тенанта и включается позже.

Документы: [`TECHNICAL_PLAN.md`](./TECHNICAL_PLAN.md) — техплан, [`PLAN.md`](./PLAN.md) — анализ рисков.

## Архитектура

- **`apps/api`** — backend на NestJS: auth по ролям (валидация Telegram initData → JWT),
  меню с модификаторами, заказы с машиной состояний, стоп-лист, приглашения
  сотрудников, Telegram-бот (grammY), WebSocket (socket.io), очереди BullMQ
  (автоотмена непринятых заказов, уведомления).
- **`apps/tma`** — Mini App на React + Vite: роутинг по роли, экраны клиента,
  бариста и админа, корзина, live-статусы через WebSocket.
- **`packages/shared`** — общий код: enum статусов, машина состояний заказа,
  zod-схемы DTO, расчёт цены. Источник истины для фронта и бэка.

Ключевые технические решения (подробнее — в техплане):
`tenant_id` во всех таблицах + RLS; снапшот позиций заказа в JSONB; деньги в
копейках; цена всегда пересчитывается на сервере; push-уведомления бота — основной
канал доставки заказов бариста (Mini App не живёт в фоне), WebSocket — ускоритель.

## Быстрый старт (локально)

Требуется Node 20+, pnpm 10+, Docker (Postgres, Redis, MinIO).

```bash
pnpm install
cp .env.example apps/api/.env        # впишите TELEGRAM_BOT_TOKEN
pnpm infra:up                        # postgres + redis + minio

cd apps/api
pnpm prisma:generate
pnpm prisma db push                  # применить схему (или db:migrate для миграций)
pnpm db:rls                          # включить RLS-политики (defense-in-depth)
pnpm db:seed                         # демо-кофейня «Demo Coffee» (slug: demo)

# два терминала:
pnpm --filter @coffee/api dev        # API на :3000
pnpm --filter @coffee/tma dev        # Mini App на :5173
```

Для теста Mini App с реального телефона поднимите туннель (например
`cloudflared tunnel --url http://localhost:5173`) и укажите его как Web App URL
в настройках бота у @BotFather. Открыть меню демо-кофейни:
`?startapp=demo`.

Сид создаёт владельца и бариста, привязанных к Telegram id из
`SEED_OWNER_TG_ID` / `SEED_BARISTA_TG_ID` (по умолчанию — плейсхолдеры; впишите
свои id, чтобы зайти под этими ролями).

## Статус

Реализовано ядро MVP: авторизация по ролям, меню с модификаторами и стоп-листом,
создание заказа с серверным расчётом цены, машина состояний, лента бариста с
кнопками статусов, WebSocket, Telegram-бот и уведомления, автоотмена непринятых
заказов, приглашение сотрудников по ссылке, базовая админка (сотрудники, точки,
стоп-лист). Не реализовано (следующие этапы): онлайн-оплата (ЮKassa), загрузка
фото меню в S3, полноценный редактор меню в админке, биллинг подписки, веб-версия
для клиента, собственный бот тенанта.

## Онлайн-оплата (ЮKassa)

Интеграция per-tenant: каждая кофейня подключает **свой** эквайринг, платформа
денег не касается и хранит только ключи (зашифрованными).

### 1. В личном кабинете ЮKassa

1. `Настройки` → выпустить **секретный ключ**. Показывается один раз.
2. `Настройки` → `Способы оплаты` — включить банковскую карту и СБП.
   Проверить, что реально включилось, можно запросом `/v3/me` (см. ниже).
3. `Интеграция` → `HTTP-уведомления`:
   - URL: `https://<ваш-домен>/v1/webhooks/yookassa/<tenantId>`
   - события: `payment.succeeded`, `payment.canceled`
4. Фискализация (54-ФЗ): либо своя касса кофейни, либо облачная касса ЮKassa.
   Во втором случае выставить `YOOKASSA_RECEIPT_ENABLED=true` — тогда сервис
   передаёт состав чека вместе с платежом.

### 2. Переменные окружения

| Переменная | Обязательна | Значение |
|---|---|---|
| `SECRETS_ENCRYPTION_KEY` | да | 32 случайных байта: `openssl rand -hex 32`. Без него секрет в БД не шифруется по-настоящему. |
| `YOOKASSA_SHOP_ID` | да* | shopId магазина. |
| `YOOKASSA_SECRET_KEY` | да* | Секретный ключ магазина. |
| `YOOKASSA_RETURN_URL` | да | Куда вернуть клиента после оплаты: `https://t.me/<бот>/<приложение>`. |
| `YOOKASSA_RECEIPT_ENABLED` | нет | `true`, если чек 54-ФЗ формирует ЮKassa. По умолчанию `false`. |
| `YOOKASSA_VAT_CODE` | нет | Ставка НДС для позиций чека. `1` — без НДС (УСН), по умолчанию. |
| `YOOKASSA_WEBHOOK_IPS` | нет | Список разрешённых адресов уведомлений. По умолчанию — официальные подсети ЮKassa. Пустая строка отключает проверку. |

\* Ключи можно не класть в окружение, а записать через API (см. п.4) — тогда они
лягут в таблицу `payment_credential` в зашифрованном виде. Окружение —
фолбэк для установки с одной кофейней.

### 3. Включить онлайн-режим у кофейни

```sql
UPDATE tenant SET payment_mode = 'online' WHERE slug = '<ваш-slug>';
```

Пока `payment_mode = 'offline'`, заказы оформляются с оплатой на кассе,
и платёжный модуль не задействуется.

### 4. Проверка

Диагностика (JWT владельца) — показывает, откуда взяты ключи, статус магазина
и **реально включённые способы оплаты**:

```
GET /v1/admin/payments/diagnostics
```

Записать ключи в БД вместо окружения:

```
PUT /v1/admin/payments/credentials
{ "shopId": "1438394", "secretKey": "..." }
```

То же самое напрямую у провайдера:

```bash
curl -s https://api.yookassa.ru/v3/me -u '<shopId>:<секретный ключ>'
```

Пустой `payment_methods`, `status: disabled` или `fiscalization_enabled: false`
— причина, по которой оплата не проходит, находится в кабинете ЮKassa, а не в коде.

### Как это работает

- `POST /v1/orders` при `payment_mode = online` создаёт заказ в статусе
  `pending_payment`. Бариста его **не видит** — заказ не подтверждён.
- `POST /v1/orders/:id/pay` создаёт платёж и возвращает `confirmationUrl`.
  Повторный вызов отдаёт ту же ссылку — второй платёж не создаётся.
- `POST /v1/webhooks/yookassa/:tenantId` принимает уведомление. Подписи у
  уведомлений нет, поэтому телу не доверяем: берём только id платежа и
  перезапрашиваем объект через API. Плюс проверка IP отправителя.
- После `succeeded` заказ переходит в `paid` — и только тогда появляется в
  ленте бариста и в боте.
- Отмена или отклонение оплаченного заказа ставит **возврат** в очередь
  (5 попыток с экспоненциальной паузой).
- Раз в минуту идёт сверка зависших платежей: если уведомление не дошло,
  статус всё равно подтянется.
- Неоплаченный заказ автоматически отменяется через 15 минут
  (`PAYMENT_TIMEOUT_MINUTES`).
