# План технической реализации

Платформа предзаказа кофе. Всё живёт в **одном Telegram Mini App с тремя ролями**: клиент, бариста, админ (владелец). Без интеграции с кассой/POS — заказ из приложения бариста пробивает по своей кассе как обычную продажу. Мультитенантная (одна инсталляция — много кофеен), white-label.

---

## 1. Общая архитектура

```
                Telegram Mini App (одно приложение, роль определяет экран)
                ┌──────────────┬──────────────┬──────────────┐
                │   Клиент     │   Бариста    │    Админ     │
                │ меню, заказ, │ лента заказов│ меню, цены,  │
                │ статус       │ статусы, стоп│ сотрудники   │
                └──────┬───────┴──────┬───────┴──────┬───────┘
                       ▼              ▼              ▼
                ┌─────────────────────────────────────────┐
                │  Backend-монолит (NestJS, REST + WS)    │──▶ PostgreSQL
                │  вебхуки Telegram-бота и платежей       │──▶ Redis (pub/sub, джобы)
                └─────────────────────────────────────────┘──▶ S3 (фото меню)
                       ▲
                Telegram Bot API — push-уведомления всем трём ролям
```

Принципы:
- **Модульный монолит**, не микросервисы. Один деплой, масштабируется репликами.
- **Один фронтенд** — Mini App; после авторизации бэкенд отдаёт роль, роутер показывает нужный интерфейс. Никаких отдельных сайтов/панелей на MVP (web-версию для клиента можно добавить позже из той же кодовой базы).
- **Бот — обязательная часть системы, а не довесок.** Mini App не работает в фоне: если бариста свернул Telegram или погас экран, приложение «мертво». Поэтому каждый новый заказ дублируется сообщением от бота — это нативный push со звуком, который бариста не пропустит. Кнопка «Открыть заказ» в сообщении ведёт обратно в Mini App.
- **Мультитенантность на уровне строк**: `tenant_id` в каждой бизнес-таблице + PostgreSQL Row-Level Security как страховка.
- Всё время в БД — UTC; таймзона хранится у точки (`location.timezone`).

## 2. Оплата — два режима

Раз к кассе не привязываемся, режим оплаты — настройка тенанта:

1. **«Оплата при получении» (MVP, режим по умолчанию).** Приложение — только предзаказ: клиент заказывает, бариста готовит, клиент платит на кассе как обычно. Ноль интеграций, ноль 54-ФЗ, ноль возвратов — кофейня пробивает чек своей кассой как всегда. Запускаемся с этим.
2. **Онлайн-оплата (фаза 2, опция тарифа).** Кофейня подключает свой эквайринг (ЮKassa), чек 54-ФЗ формирует сторона провайдера по её настройкам, платформа денег не касается. Включается флагом `tenant.payment_mode = online`.

Это снимает главный риск запуска: продукт можно продавать и внедрять за день, не дожидаясь платёжного контура.

## 5. Роли и авторизация

Авторизация одна на всех: Mini App передаёт `initData` → бэкенд валидирует HMAC-подпись (токен бота, TTL ≤ 1 ч) → ищет `tg_user_id` в `staff_user` тенанта:

| Найден как | Роль в JWT | Экран |
|---|---|---|
| owner/manager | `admin` | админка |
| barista | `barista` | лента заказов |
| не найден | `client` | меню |

- JWT (access 15 мин + refresh) несёт `tenant_id`, `role`, `sub`. Guard сверяет роль и тенанта, выставляет RLS-переменную на соединение.
- **Назначение бариста без боли:** админ в своём экране жмёт «Добавить сотрудника» → бот выдаёт одноразовую ссылку-приглашение `t.me/bot/app?startapp=join_<token>` → бариста открывает её, его `tg_user_id` привязывается к точке. Никаких PIN-кодов и паролей.
- Сотрудник может переключиться в режим клиента (заказать себе кофе) — просто свитч в UI, роль в токене остаётся.
- Тенант определяется из `start_param`: `t.me/bot/app?startapp=<tenant_slug>` (QR-код с этой ссылкой — на кассе кофейни).

## 6. Модель данных (ядро)

```
tenant            (id, name, slug, plan, status, branding jsonb, payment_mode: offline|online)
location          (id, tenant_id, name, address, timezone, schedule jsonb,
                   is_accepting_orders bool, max_orders_per_slot int)
staff_user        (id, tenant_id, location_id, role: owner|manager|barista,
                   tg_user_id, name, invited_by, is_active)
customer          (id, tg_user_id, name, created_at)                -- глобальный
tenant_customer   (tenant_id, customer_id, first_order_at, orders_count)

category          (id, tenant_id, name, sort, is_active)
product           (id, tenant_id, category_id, name, description, photo_url,
                   base_price int, sort, is_active)
modifier_group    (id, tenant_id, name, min_select, max_select, is_required)
product_modifier_group (product_id, group_id, sort)
modifier_option   (id, group_id, name, price_delta int, is_default)
stop_list         (location_id, product_id? | modifier_option_id?, until_ts?)

order             (id, tenant_id, location_id, customer_id, number,   -- короткий номер дня: A-17
                   status, items jsonb,                               -- СНАПШОТ позиций с ценами
                   total int, payment_mode, ready_at_requested, ready_at_promised,
                   comment, created_at, status_history jsonb)
payment           (id, order_id, provider, provider_payment_id, status,
                   amount int, idempotency_key uuid, payload jsonb)   -- фаза 2
notification_log  (id, tenant_id, order_id, channel, status, payload)
```

Ключевые решения:
- **`order.items` — JSONB-снапшот** (названия, цены, модификаторы на момент заказа): меню меняется, заказ — нет.
- Деньги — **integer в копейках**, никогда float.
- Индексы: `(tenant_id, status, created_at)` на orders; уникальный `(tenant_id, slug)`.
- RLS-политика на все tenant-таблицы: `tenant_id = current_setting('app.tenant_id')::uuid`.

## 7. Машина состояний заказа

Режим «оплата при получении» (MVP):

```
created ──бариста принял──▶ accepted ──▶ preparing ──▶ ready ──▶ completed
   │                            │
   │ не принят за N мин         │ отказ бариста (стоп-лист и т.п.)
   ▼ (BullMQ delayed job)       ▼
auto_cancelled               rejected
```

Режим онлайн-оплаты добавляет `created → pending_payment → paid` перед `accepted` и автовозвраты при отмене (фаза 2).

- Переходы — только через `OrderService.transition(orderId, event)` с проверкой допустимости; каждый переход пишется в `status_history` и публикуется в Redis pub/sub → WS-комнаты `order:{id}` (клиент) и `location:{id}` (бариста).
- Автоотмена непринятого заказа: отложенная джоба BullMQ + уведомление клиенту «кофейня не может принять заказ».

## 8. Уведомления — двухканальная схема

Главная техническая особенность выбранной архитектуры: **бариста работает в Mini App, а Mini App не живёт в фоне**. Поэтому:

1. **Канал 1 — WebSocket** внутри открытого Mini App: лента бариста обновляется мгновенно, новый заказ — звук + вибрация (`HapticFeedback`), пока экран открыт.
2. **Канал 2 — сообщение от бота (основной по надёжности):** на каждый новый заказ бот шлёт бариста точки (и владельцу — настраивается) сообщение «Новый заказ A-17: капучино большой, к 9:15» с inline-кнопкой «Открыть» (deep-link в Mini App на карточку заказа). Это нативный push Telegram — сработает при свёрнутом приложении и погасшем экране.
3. Клиенту статусы («Принят, будет готов к 9:15», «Готов!») — тоже сообщениями бота: бесплатно и не требует держать Mini App открытым.
4. Если заказ не принят за 3 минуты — эскалация: повторное сообщение бариста + владельцу.
5. Все отправки — через BullMQ с ретраями, лог в `notification_log`.

WS — только «пинок», источник истины — REST: при любом реконнекте лента рефетчится.

## 9. API (основные контуры, REST)

```
Клиент:
  GET  /v1/menu?location=            — меню с учётом стоп-листа (кеш Redis 30с)
  POST /v1/orders                    — создать заказ (пересчёт цены на сервере!)
  GET  /v1/orders/:id                — статус (+ WS подписка)
  GET  /v1/orders/my                 — история

Бариста:
  GET   /v1/staff/orders?status=active
  POST  /v1/staff/orders/:id/accept | reject | preparing | ready | complete
  PUT   /v1/staff/stop-list          — тумблеры позиций/модификаторов
  PUT   /v1/staff/location/pause     — приостановить приём заказов

Админ:
  CRUD /v1/admin/{categories,products,modifier-groups,locations}
  POST /v1/admin/staff/invite        — одноразовая ссылка-приглашение
  GET  /v1/admin/stats/…

Вебхуки:
  POST /v1/webhooks/telegram/:botId  — апдейты бота
  POST /v1/webhooks/yookassa/:tenantId — фаза 2
```

Критично: **сумма заказа всегда пересчитывается на сервере** из актуального меню; при расхождении с клиентской ценой — 409 с новым прайсом.

## 10. Mini App: три экрана в одном SPA

Роутинг по роли из JWT; общая темизация из `themeParams` Telegram + брендинг тенанта (CSS-переменные из `tenant.branding`).

**Клиент:** точка → меню → карточка с модификаторами → корзина → время готовности (слоты с учётом `max_orders_per_slot`) → подтверждение → статус-трекер. Корзина в Zustand + persist в `cloudStorage`.

**Бариста:** лента активных заказов крупными карточками (планшет или телефон), кнопки-статусы, стоп-лист в 2 клика, пауза точки. Честное ограничение: держать экран открытым весь пик смены Telegram не даст — рабочая модель «услышал push от бота → открыл → принял». Для кофеен с планшетом на стойке позже можно дать ту же ленту как обычную веб-страницу (то же SPA по URL с токеном точки) — планшет умеет не гаснуть, звук в цикле работает; это опция, не требование.

**Админ:** меню (drag&drop сортировка, фото через пресайн-URL в S3, ресайз sharp), точки и расписание, сотрудники (приглашения), простая статистика заказов.

## 11. Инфраструктура и эксплуатация

- **Dev:** `docker compose up` — Postgres, Redis, MinIO, api, tma; сиды с демо-кофейней; cloudflared-туннель для теста Mini App с реального телефона.
- **CI (GitHub Actions):** lint → typecheck → unit → build → миграции staging → e2e → деплой по тегу.
- **Prod (старт):** 1 VPS в РФ (152-ФЗ), Docker Compose, nginx + certbot, ежедневные бэкапы Postgres (pg_dump → S3, тест восстановления ежемесячно).
- **Мониторинг:** Sentry (front+back), pino-логи, Uptime Kuma; бизнес-алерты в служебный TG-канал: заказ не принят за 3 мин, ошибки доставки уведомлений, всплеск отказов.

## 12. Тестирование

- Unit: калькулятор цены (модификаторы, краевые случаи), машина состояний, валидация initData.
- Integration: RLS-изоляция («тенант А не видит заказы тенанта Б» — обязательный тест), приглашения сотрудников, идемпотентность вебхуков бота.
- E2E (Playwright): happy path клиент→бариста на каждом релизе.
- Ручное: Mini App на реальных iOS + Android — WebView различаются.

## 13. Этапы реализации

### Этап 1 — фундамент (2 недели)
Монорепо, docker-compose, CI, скелет NestJS, схема БД + миграции + RLS, бот-«скелет» (вебхук, deep-links), auth: initData → роль → JWT, сиды с демо-кофейней.
**Готово, когда:** e2e «initData → JWT с ролью; запрос к чужому тенанту → 403».

### Этап 2 — меню и заказ (2 недели)
CRUD меню с модификаторами (экран админа), публичное меню со стоп-листом, создание заказа с серверным пересчётом, машина состояний, слоты времени с лимитами.
**Готово, когда:** клиент собирает заказ с модификаторами, заказ появляется в БД с корректной суммой.

### Этап 3 — экран бариста и уведомления (2 недели)
Лента заказов + WS, кнопки статусов, стоп-лист с телефона, push-сообщения бота на все события (новый заказ → бариста, статусы → клиенту), эскалация и автоотмена через BullMQ, приглашение сотрудников по ссылке.
**Готово, когда:** полный цикл на двух телефонах: клиент заказал → бариста получил push → принял → клиент получил «готов». Это и есть MVP.

### Этап 4 — полировка и пилот (2–3 недели)
Брендинг тенанта, история заказов, статистика админа, онбординг-мастер (создать кофейню → меню → QR-код), мониторинг и бизнес-алерты, багфиксы по пилоту в реальной кофейне.
**Готово, когда:** новая кофейня подключается без разработчика; пилот принимает реальные заказы.

### Этап 5 — онлайн-оплата (2–3 недели, по спросу)
ЮKassa per-tenant, `pending_payment/paid` в FSM, идемпотентность, вебхуки, автовозвраты, cron-сверка зависших платежей, чеки 54-ФЗ на стороне провайдера.

### Этап 6 — рост (по запросам клиентов)
Веб-версия клиента из той же кодовой базы (Telegram Login), собственный бот тенанта (свой токен), лояльность/промокоды, планшетный режим ленты бариста, биллинг подписки платформы.

**Итого до работающего MVP (этапы 1–3): ~6 недель; до продаваемого продукта (этап 4): ~8–9 недель силами 1–2 разработчиков.**

## 14. Технические решения, зафиксированные заранее (чтобы не переделывать)

1. `tenant_id` + RLS с первого коммита — ретрофит мультитенантности дороже всего остального вместе взятого.
2. Снапшот заказа в JSONB — заказы неизменяемы, меню волатильно.
3. Деньги в копейках (int), пересчёт суммы только на сервере.
4. Push-сообщения бота — основной канал доставки заказов бариста; WS — ускоритель для открытого экрана, не гарантия.
5. Оплата — режим тенанта (`offline`/`online`): старт без платёжного контура, онлайн-оплата подключается флагом, а не переписыванием.
6. Монолит до тех пор, пока не заболит; Redis + BullMQ дают весь нужный асинхрон.
